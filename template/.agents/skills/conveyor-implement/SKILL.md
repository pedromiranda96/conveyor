# Conveyor Implement

Translate decisions into code for the project's existing stack and keep `.conveyor/generated/implementation.md` as a concise record. Infer the request's scope instead of requiring the user to select a mode. Conveyor's source/artifact paths are stack-independent; the project's framework, package manager, and conventions determine where and how code is written.

Treat brief and design as read-only inputs. Write site code and the implementation record; leave corrections to other stage artifacts to their owning skills.

## Implementation/review boundary

**NEVER invoke `conveyor-review` from implementation.** Do not switch to a reviewer role, launch/delegate a review subagent, schedule a review, or ask another chat/agent to perform it on your behalf. This prohibition also applies to combined requests such as "implement and review" or "fix and review again": complete the implementation and its technical checks, then return a handoff for the user to invoke review separately.

You may read existing independent review artifacts as fix inputs. You must not create or modify files in `.conveyor/generated/reviews/`, issue an independent review verdict, or declare review findings independently closed. Review is a separate user-invoked stage conducted in a different context or by a fresh-context reviewer agent.

**Looking is allowed; judging is not.** When rendering helps you build, debug, or confirm that a change you just made renders as intended, you may view the site with available tools, scoped to the areas this request touches. This is working inspection, not verification. Do not delegate it to another agent, sweep pages or viewports beyond your change, or run review's checks on your own work. Nothing you observe in the rendered site counts as evidence, including results of browser-backed tests: record only non-browser build, lint, type checks, source inspection, and non-browser tests as verification, keep visual and interaction findings changed-but-unverified, and never write review artifacts or declare findings closed. You may note problems you saw but left unfixed; do not record that something looked correct.

Read `AGENTS.md`, `.conveyor/workflow.md`, the brief, embedded design JSON/documentation and any included examples, current code, and the existing implementation record. Read [implementation contract](references/implementation-contract.md). A page specimen is not a prerequisite for implementation. Discover current canonical brand files, optional guidance, and design-bound media/reference views; stale inventory does not establish that a newly supplied logo is absent. Identify the actual stack from the project; consult its relevant official guides and documentation required by `AGENTS.md`. Determine the styling approach by the workflow's order, checking the installed Tailwind version and integration when present, and record the approach and reason. Do not replace the stack or an established styling system without a request.

## Choose scope

- **Initial build:** implement the requested scope from the brief and established design direction, including real visitor actions. A request for a landing page builds that page; it does not imply building every content requirement as a separate page. Choose suitable routes, content placement, and navigation within scope, honoring explicit user choices. An absent page plan or undocumented component is not an incomplete design by itself. If either artifact is missing or consequentially incomplete, identify the missing input rather than inventing a replacement workflow. Work on independent parts while awaiting necessary answers.
- **Extend or reorganize:** add pages, routes, sections, or components, or split/merge existing pages using the established direction. The request authorizes the necessary structure and navigation changes within its scope, including changing between one page and multiple pages. Preserve unrelated work and applicable visual requirements. Choose layouts and derive new component patterns from the design's principles; do not require prior page/component specifications or send ordinary additions back to design. Ask only about consequential missing content or conflicting requirements, and continue independent work while awaiting answers.
- **Small tweak:** change the requested area and preserve surrounding code, composition, and accepted refinements. Existing source is part of the project context, not something to regenerate wholesale. Missing optional artifacts need not prevent a clearly specified local fix.
- **Review fixes:** read the review selected by path/ID or unambiguous request context. If multiple reviews could be meant, ask which; do not guess. Address all required findings by default, or the user's explicit subset. Advisory findings need a request. Confirm findings against current code before changing it: a stale review may describe a problem already fixed.
- **Apply design revision:** reconcile the requested design changes with the existing site while preserving refinements outside their scope. Do not treat every new artifact revision as permission to rebuild the entire site.

For a small tweak with broader unapplied design changes, make the tweak and mention the remaining changes. Apply concrete user-requested visual adjustments, including shared values such as a specified button color, directly to site code and record them in `implementation.md`. Preserve their exact values/behavior and scope in the current-state summary so future work carries them forward over older design decisions. Do not edit brief/design or require a design invocation merely to synchronize documentation. Local composition and new component patterns within the direction need only the implementation entry.

If the request requires exploring or choosing a new visual direction, or lacks necessary business/content decisions, record the specific handoff to design or brief and continue independent work. Do not silently invoke their skills. Distinguish a concrete requested adjustment from permission to redesign.

Record the pages/routes, content, and navigation actually affected by the request, along with relevant pending work. Adding a page or reorganizing existing content within the established direction needs no new brief/design revision. Treat older design `pages` lists as context: preserve applicable visual requirements, follow the user's requested scope, and record where affected content/relationships moved.

Use review ownership to distinguish code defects from upstream brief/design decisions. Apply concrete implementation corrections within scope and explicit user-requested adjustments; findings needing missing business decisions or exploration of a new direction remain unresolved handoffs to the owning stage. Do not reinterpret an aesthetic suggestion as permission to redesign. Mention newly changed brand/reference inputs without expanding a small tweak into an unrequested migration or rebrand.

## Implement

Read the installed `frontend-design` skill to guide coding decisions about hierarchy, spacing, responsive rules, copy, and restraint against the existing direction. Its screenshot self-critique is working inspection under this skill's boundary: it informs the build, not the implementation record. Do not use it to invent a competing design or impose a new aesthetic approval step.

Preserve the design's source-to-target relationships and purposeful media treatments, not merely its token list. Inspect the reference views for the areas being implemented. Do not replace a specified collage, image treatment, or interface composition with generic text panels just because that is easier to code; follow the existing asset-choice policy when a required source is missing.

Treat required foundations/rules and explicit preservation decisions as constraints, and illustrative examples as demonstrations of their labeled purpose. Refine composition, cropping, responsive behavior, and finish within the chosen direction; do not copy an unfinished page example's incidental arrangement or defects. Consult original references instead of treating an intermediate mockup as their replacement. Resolve actual conflicts with requirements, but do not ask permission for ordinary improvements in explicitly open areas. Record those refinements in the implementation record.

Use `.conveyor/brand/` as supplied originals and `.conveyor/generated/media/` as canonical newly selected/generated media. Copy, optimize, or import assets into locations appropriate to the actual stack without changing originals; record source-to-destination mappings, variant/role, and any transformation. No universal `src/assets/` or `public/` layout is required. Respect older recorded paths unless migration is requested. Keep inspection crops out of deployable media.

Follow the workflow's styling policy for the recorded approach, with component files for reused UI. With Tailwind, use utilities directly in markup and shared theme tokens: no `.hero-title`, handwritten component CSS, giant authored stylesheets, or `@apply` classes. Tailwind v4 tokens belong in `@theme`; font loading may use necessary `@font-face`. Keep full utility strings discoverable by Tailwind, including component variants. Use arbitrary utilities only for truly one-off layout measurements, not to bypass the palette/type scale. With plain CSS or an established system, map the tokens once and keep component styles scoped to their components.

Preserve companion line heights and complete typography recipes. Do not add generic line-height overrides, such as `leading-*` utilities, that override token values unless the design or a recorded explicit user adjustment specifies that override. Check source recipes for unintended overrides; resolved browser typography must be verified by independent review.

Use the design's selected palette and documented color-role/combination mappings together with recorded explicit user adjustments, not hues re-extracted from the references or photos. Follow explicit supporting-color restrictions. For older artifacts use their recorded color tokens and direction; absence of the new `palette` field does not authorize choosing different colors. A concrete requested color change can be implemented and recorded here; exploring a new palette belongs to design.

Respect font loading, responsive transformations, keyboard focus, reduced motion, semantic structure, and the actual CTA destinations. Do not invent a form backend, working contact destination, or business proof. Missing imagery follows the shared choice policy; do not source or generate it without that choice. Record deliberate placeholders and nonfunctional integrations as unresolved, rather than presenting them as completed.

## Verify and record

Run existing non-browser checks appropriate to the change; for an initial build or theme/component changes, verify the production build. Inspect check commands/configuration before running ambiguous test scripts so you know which results count as non-browser verification. Leave rendered verification and visual acceptance to independent review. Record checks actually performed and their results, including limits; do not claim rendered behavior or visual quality passed from source, build, or working-inspection evidence. These are technical implementation checks, not a formal review artifact or an independent verdict.

When a server is needed, follow the project's `AGENTS.md` and stack commands. When they define a background mode or server management commands, use them; do not replace a required background mode with a foreground command or `&`. Use the project's package-manager command wrapper when needed.

Append an implementation entry with affected files, artifact revisions, non-browser checks, pending scope, and review/finding references. For review fixes, distinguish addressed-and-verified, changed-but-unverified, already-resolved, and unresolved findings; these describe technical implementation evidence, not independent closure. Rendered/interaction findings remain pending independent verification even after code corrections and a passing build. Do not edit the original review or declare its findings independently closed. Finish with what changed, technical verification, the record link, and remaining issues. Stop after this handoff. The user must invoke the next independent review as a separate step; implementation never starts or delegates it.
