# Conveyor Review

Produce `.conveyor/generated/reviews/<REVIEW_ID>.md`. Read `.conveyor/workflow.md` and [review contract](references/review-contract.md). One invocation performs one review, not an automatic correction loop.

Review starts only as a separate user-invoked stage, never through implementation's automatic handoff or delegation. The agent/context that implemented or fixed the code must not inspect it as the review worker or issue its verdict. For a separate explicit user review request in a chat containing implementation history, dispatch a fresh-context worker using the rules below; if independent context is unavailable, ask the user to invoke review in another chat. Do not reinterpret an implementation request as review authorization.

## Fresh-context dispatch

When this skill is invoked, delegate to a reviewer subagent with fresh context (`fork_turns: "none"` or the tool's equivalent), when supported. Pass only the project root, this skill path, brief/design paths, canonical brand/reference directories, current site URL if known, requested scope, and optional previous review path. Do not pass implementation conversation history, the implementer's reasoning, intended findings, or claims that fixes worked. Tell the child it is the **review worker**, so it executes the inspection below without delegating recursively. Wait for its artifact, then relay its result.

The review worker reads artifacts and source itself. Implementation record metadata can establish which revision/scope was applied; its claimed success is not evidence. Do not send unrelated source snippets selected to suggest a verdict.

Read active explicit user adjustments and their referenced implementation entries as requirement context alongside the design. Respect recorded request provenance and scope; an authorized adjustment superseding an older design value is not drift solely because design was not rewritten. Agent-derived refinements or assertions of success do not establish user authorization or correctness. Independently verify the resulting code/site against the effective requirements, and report consequential ambiguity rather than inventing approval.

If fresh-context delegation is unavailable, ask the user to invoke this skill in a separate chat and explain that the skill requires independent context. A reviewer already explicitly invoked in a separate chat can execute as the worker when delegation is unavailable. Do not substitute self-review in the implementation conversation. Browser-tool fallback and fresh-context fallback are separate concerns.

## Independent inspection (review worker)

Read the brief, design JSON/rules/specimens, current `.conveyor/brand/` materials/guidance, original reference views, current source, and previous review if specified. Inspect related detail views as views of the same source. Missing artifacts or unreadable reference details make corresponding checks unverified, not passed; an optional missing brand package is not itself a defect. Honor explicit scope and user-authorized exceptions recorded in artifacts. Allocate a new review ID, keeping prior artifacts intact. Capture the code/artifact/input snapshot before inspecting so conclusions are tied to the state reviewed. Older artifacts lacking newly introduced contract fields remain readable; do not classify absence of new metadata alone as a visual defect.

Discover tools actually available. Prefer browser automation capable of navigation, computed-style inspection, interaction, and screenshots. Use computer use for visual/interaction evidence when available, without claiming computed-style checks it cannot perform. Do not install tools silently. If neither is available, perform source review, mark browser checks unverified, and recommend a concrete available route or setup for finishing them.

Use a provided running URL or discover/start the local server according to the project's stack and `AGENTS.md`, using any background mode or server management commands they define. Do not start a server for source-only review, stop a server you did not start, or bypass project instructions. Inspect source/configuration independently even when a browser is available.

Check by default:

- **Reference fidelity:** compare original composition/detail views with the design's stated relationships, any included examples for their labeled purpose, and the implemented site. Page specimens are optional; their absence alone is not a defect or missing coverage. Verify actual site composition against required relationships and requested fidelity, not an illustrative arrangement. Check hierarchy/proportions, media composition/layering, surface roles, and section rhythm. Respect brand/content adaptations and recorded exceptions; avoid fabricated similarity scores or pixel-perfect demands when viewports/content differ. Distinguish lost reference features in the design from implementation deviations. A site matching its design does not establish that the design matches the requested reference.
- **Brand:** verify supplied logo/variant, proportions, background legibility, explicit palette/type rules, and actual source-to-deployment mappings. Do not call an inferred color official, demand an unavailable optional logo, or mistake a reference's clients/partners for the business's credentials. Newly added brand files are current inputs even if an old brief still lists them as missing; record scope/freshness differences rather than assuming they were already applied.

- **Design:** actual role-appropriate palette usage, font loading and resolved typography, spacing/container rules, components/states, and composition. Inspect computed values when possible; normalize color formats and evaluate fluid/responsive values at the tested viewport. Allowed alpha/state variants and one-off layout values are not automatically drift. Tokens existing in source does not prove that rendered values match them.
- **Palette decision:** check the recorded source/selection against user or brand instructions and actual role/combination usage. Supplied colors must not be silently replaced by reference hues; supporting additions must be identified and allowed. Do not penalize intentional recoloring or require colors from photographs. Competing reference palettes need a recorded selection/delegation rather than an unexplained blend. If an older artifact lacks `palette`, trace available tokens/direction/guidance and report any real uncertainty without treating the missing field alone as a defect.
- **Brief/content:** required content within the declared scope, factual claims, audience/action alignment, contact destinations, and declared placeholders. Trace content and recorded structure changes against actual routes/navigation, using code and rendered evidence when available. Content outside a scoped page delivery is pending broader work, not automatically an implementation defect; broken visitor actions or missing content required for that page remain findings. An older design page list is not a closed scope; new pages/components within the direction do not themselves require a design revision. Preserve applicable explicit visual requirements and distinguish a newly changed requirement from an implementation mistake where provenance makes that clear.
- **Responsive/interaction:** narrow mobile and desktop, relevant breakpoint transitions, overflow/clipping, navigation, links, contact actions, and relevant interactive controls.
- **Basic accessibility:** semantics/heading structure, labels and alternative text, keyboard reachability, visible focus, contrast, and reduced-motion behavior when relevant. State the tested scope, not a comprehensive certification.
- **Code contract:** the styling approach recorded in `implementation.md` and the workflow's rules for it: token usage, prohibited component CSS/classes with Tailwind or unscoped page-wide component styles with plain CSS, repeated UI component reuse, and inappropriate hardcoded palette/type values. Do not flag utility classes emitted by Tailwind as handwritten CSS. An unrecorded approach, or one that departs from the workflow's styling order without a stated reason, is a finding.

Choose viewports appropriate to the design (at least narrow mobile and desktop when rendered review is possible) and record dimensions. Save useful screenshots under `.conveyor/generated/reviews/<REVIEW_ID>/` and link them from the report. Do not send messages, submit real contact forms, or trigger external side effects to prove an interaction; inspect destinations and exercise safe local behavior.

Required findings need an evidenced requirement violation or usability defect. An explicitly requested reference relationship can be a requirement; a reviewer's preferred new direction cannot. Subjective aesthetic suggestions are advisory, with rationale. An inability to verify is coverage missing, not an invented failure. For each finding include owning stage (brief/design/implement), exact location, expectation, observation, evidence, and acceptance criterion; avoid prescribing a redesign when a scoped correction suffices. Upstream omissions may need a design revision rather than another implementation pass. Keep source-to-design and design-to-site coverage separate so internal consistency cannot hide lost fidelity.

Do not require pixel matching to page examples or promote their incidental details into rules. An implementation refinement within documented freedom is not drift merely because it differs from a sample. Cite an explicit requirement, preserved reference relationship, or usability defect before making such a finding required. Respect existing user-approved composition requirements; optional previews do not cancel those decisions.

For rechecks, independently verify previous findings and inspect affected areas for regressions. Reference previous finding IDs as resolved, still-open, or unverified; do not copy the prior verdict. If code/artifacts change during inspection, disclose the mismatch and recheck affected evidence or mark it unverified.

Write the contract's artifact with `needs-fixes`, `incomplete`, or `pass` outcome. Do not change application code, brief, design, or implementation history, and do not alter earlier reviews. Return the report link, required/advisory counts, coverage gaps, and next manual action. The implementer may fix it on the user's next request.
